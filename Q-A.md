# Q&A

## 1. Пермишены: зачем Accessibility? Он для автозапуска или для микрофона?

Это **три независимые вещи**, друг друга не заменяют:

| Что | Какой механизм | Где в коде | Когда запрашивается |
|---|---|---|---|
| **Microphone** | TCC-пермишен «Микрофон» (Privacy & Security → Microphone) | `setup_app.py:26` (`NSMicrophoneUsageDescription`), `listen/audio.py:22` | macOS сам показывает системный диалог при первом открытии `InputStream` (т.е. при первой записи) |
| **Accessibility** | TCC-пермишен «Управление компьютером» (Privacy & Security → Accessibility) | `listen/hotkey.py:20`, `listen/paste.py:29` | при создании event tap / первой вставке текста |
| **Автозапуск** | LaunchAgent (`~/Library/LaunchAgents/com.valentyn.listen.plist`), **никакого TCC-пермишена не требует** | `listen/autostart.py` | никогда не «запрашивается» — включается галкой в меню |

**Accessibility нужен в любом случае — всегда, независимо от автозапуска, и он не имеет отношения к микрофону.** Он нужен для двух функций:

1. **Глобальный хоткей (правый Option).** `listen/hotkey.py:20` создает `CGEventTapCreate(kCGSessionEventTap, …)` — перехватчик клавиатурных событий **всей сессии**, т.е. событий, предназначенных другим приложениям. macOS такое разрешает только «доверенным» accessibility-клиентам. Без пермишена `CGEventTapCreate` возвращает `None`, и `hotkey.start()` бросает RuntimeError (см. сообщение в `listen/hotkey.py:29-33`). Без этого приложение в принципе не работает — хоткей не сработает.
2. **Вставка текста.** `listen/paste.py:29-36` синтезирует нажатие ⌘V через `CGEventPost` в чужое (активное) приложение — это тоже «вставлять события ввода от имени пользователя» и тоже гейтится Accessibility.

Итого по вопросу: Accessibility ≠ автозапуск и Accessibility ≠ микрофон. Микрофон — отдельный TCC-диалог (`NSMicrophoneUsageDescription` в `setup_app.py`), он спрашивается системой при первой записи. Accessibility обязателен всегда, даже если приложение запускается вручную и только что, — потому что читать чужие клавиши и слать ⌘V нельзя без него.

Почему тогда `app.py:192` после включения «Start at Login» открывает настройки Accessibility? Это не потому, что автозапуск требует Accessibility, а потому что **в этот момент меняется, кому выдан пермишен**: в dev-режиме (`python -m listen`) Accessibility выдан Terminal/Python, а процесс, запущенный launchd'ом из LaunchAgent, — это другой «ответственный» процесс, и macOS может потребовать выдать пермишен именно `.app`-бандлу. Открытие панели — подстраховка, чтобы пользователь проверил/выдал его в момент явного намерения (см. комментарий в `listen/__main__.py:74-77`).

Нюанс текущего поведения: без Accessibility приложение при старте падает с RuntimeError (в `listen/app.py:137` `hotkey.start()` не обернут в try/except) — macOS при этом обычно показывает системный диалог «выдать доступ», пользователь выдает, перезапускает, дальше работает. Т.е. «Accessibility спрашивается на первом запуске» — это побочный эффект попытки создать event tap, а не отдельный запрос из кода (код специально не дергает `AXIsProcessTrustedWithOptions(prompt=True)`).

## 2. Архитектура: как аудио попадает в распознавание? Есть ли HTTP-сервер и порт?

**Да, есть локальный HTTP-сервер, и по умолчанию он занимает порт 8080** — как раз тот, которого вы опасаетесь. Это **не LLM в облаке**, а локальный подпроцесс: HTTP используется только как IPC между Python-приложением и бандл-бинарем движка.

Поток данных:

```
правый Option (CGEventTap, hotkey.py)
        │  start
        ▼
audio.Recorder — sounddevice/PortAudio InputStream
16 kHz, mono, int16, кадры копятся в памяти (audio.py:22-32)
        │  второй нажатый Option → stop
        ▼
numpy concat → WAV-файл /tmp/listenit_recording.wav (audio.py:44)
        │  фоновый поток (app.py:230)
        ▼
Server.transcribe → HTTP POST multipart
http://127.0.0.1:8080/v1/audio/transcriptions  (server.py:141)
        │
        ▼
nemo-speech serve — подпроцесс на C++ (server.py:77-91)
бинарь из listen/resources/nemo-speech/, GGML/Metal-библиотеки,
модель nemotron-3.5-asr-streaming-0.6b (GGUF ~707 МБ) грузится один раз
        │  ответ {"text": ...}
        ▼
paste.paste — буфер обмена + синтетический ⌘V,
через 0.5 c буфер восстанавливается (paste.py)
```

Ключевые факты:

- **Сервер поднимается при старте приложения** (`server.py` — `self.server.start()` в `app.py:135`), в фоне (отдельный поток + подпроцесс), готовность опрашивается через `GET /ready` до 120 с (`server.py:94-113`). Модель грузится один раз и остается теплой — не на каждое нажатие.
- **Занимается порт:** `listen/config.py:21-22` — `HOST = "127.0.0.1"`, `PORT = int(os.environ.get("LISTEN_PORT", "8080"))`. Бинарь поддерживает `--host/--port` (дефолт самого бинаря тоже 8080). Слушается **только loopback 127.0.0.1** — снаружи/по сети сервер не виден, конфликт возможен только с процессами на этой же машине.
- **Если 8080 занят** другим приложением — `nemo-speech serve` не сможет забиндиться, подпроцесс умрет, `_wait_ready` увидит `poll() is not None` → состояние `FAILED`, в меню-баре будет иконка-предупреждение. Никакого фолбэка/подбора свободного порта сейчас нет.
- Распознавание **не стриминговое на уровне приложения**: фраза целиком пишется в память, после второго нажатия сохраняется в WAV и отправляется одним multipart-запросом. Никакие данные наружу не уходят — единственный сетевой участник это `127.0.0.1`.
- Порт можно поменять без правки кода: env-переменная `LISTEN_PORT` (например `launchctl setenv LISTEN_PORT 8123` или в plist LaunchAgent'а).

### Если захочется убрать конфликт с 8080

Варианты по возрастанию сложности:

1. **Выбрать свободный порт динамически в Python перед спавном**: открыть `socket.bind(("127.0.0.1", 0))`, забрать номер, закрыть, передать в `--port`. Конфликт почти невозможен (окно между закрытием сокета и биндом бинаря ничтожно).
2. Зарезервировать «неудобный» высокий порт (например 4xx-диапазон) — но это все равно договоренность, а не гарантия.
3. Заменить HTTP на прямой FFI/pipe к библиотеке — у бандла есть заголовки (`listen/resources/nemo-speech/include/`), но это уже заметно больше работы.
